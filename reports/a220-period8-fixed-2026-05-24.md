# A220 period-8 render cycle — FIXED (2026-05-24)

HP TouchPad (APQ8060/MSM8660, Adreno 220 "Leia" REV470) on mainline Linux 6.18 +
Mesa freedreno (a2xx). The long-standing **period-8 render cycle** — identical
GLES submits producing 8 cycling framebuffers, 1/8 correct, 7/8 with GMEM
tile-coverage failures — is **resolved**.

## Root cause

The GFX3D **core** clock was never reset on power-on. The legacy MSM8x60
`mach-msm/footswitch-8x60.c` issues an **extra** `clk_reset(core_clk,
ASSERT/DEASSERT)` on GFX3D power-on; mainline's GDSC asserted only
`GFX3D_AHB_RESET`. Without the core reset, the Adreno 220 core (parameter cache /
SQ banking) came up **free-running**, producing the deterministic period-8 cycle.
(Registers were invariant across the cycle — the state lived in non-register
binner/SQ SRAM, which is why ~30 register-level experiments all failed.)

This **overturns** the prior conclusion (old `gpu-cycle-of-8-*` reports) that the
fix had to be userspace HW binning. It was kernel-side.

## The fix

`drivers/clk/qcom/mmcc-msm8660.c` — add `GFX3D_RESET` to the GFX3D GDSC reset list
so the power-domain framework toggles the core reset on every power-on, alongside
the AHB reset:

```c
static struct gdsc gfx3d_gdsc = {
    .resets = (unsigned int []){ GFX3D_AHB_RESET, GFX3D_RESET },
    .reset_count = 2,
    .flags = LEGACY_FOOTSWITCH | SW_RESET,
};
```

Framework-managed (sequenced with the rail charge in `gdsc_enable`'s
LEGACY_FOOTSWITCH path) — **not** a raw `ioremap` poke. Earlier ioremap-based
GFX3D-reset attempts (`e3ffca58006e` "pulse GFX3D_RESET before each WPTR write",
`174a7b70af96` "force GDSC collapse") caused **GPU hangs** because they raced
genpd / reset a live engine; the `.resets` approach avoids both.

**Commit:** `bf2a93f33b6b` on `shr-github` (`shr-distribution/linux`), branch
`tenderloin/6.18/upstream-patches`.

## Verification

`tools/gl-capture/gl-capture-md` deterministic off-screen FBO hash test, clean boot:

| Test | Before | After |
|---|---|---|
| single-draw (no depth) | 8-way cycle, 1/8 correct | **10/10 identical** |
| single-draw, warmup OFF (`FD_A22X_WARMUP_N=0`) | cycle | ~15/16 identical |

2D / non-depth rendering is now deterministic and correct. **The Mesa per-draw
warmup may now be droppable** (warmup-off is as clean or cleaner), recovering the
~⅓ FPS it cost.

## Residual: depth-stripe non-determinism (separate, narrower bug)

Depth-tested 3D (cube/grid) still shows **vertical-stripe non-determinism**: 2-3
hash clusters per run, Δ up to 229, ~3.4% of pixels, **confined to depth-tested
pixels** (the diff mask is regular vertical dashed columns; the background is
bit-identical). Evidence: `reports/fb-captures/a220-gmem-tile-noise-2026-05-24/`
(`grid_tiled.png`, `cube_cluster_diff.png`).

Ruled out, with evidence:
- VSC binner config — `LRZ_VSC_CONTROL=0x3` latch (patch 0010) and
  `FD_MESA_DEBUG=nobin` are **both no-ops**.
- Depth precision — 16-bit *and* 24-bit (`FD_DEPTH24`) both non-deterministic.
- `FD_MESA_DEBUG=sysmem` renders **blank** on a22x (not a usable reference/fix).
- freedreno's GMEM bin sizing **is** depth-aware (`zsbuf_cpp` in the budget), so
  the depth region is correctly located — the bug is in the depth **clear** or
  depth microtile addressing, not the layout.

The discriminator is **depth**: non-depth rendering is fully deterministic;
depth-tested rendering is not. Next lever: a Mesa rebuild disabling the a22x depth
fast-clear (`fd2_clear_fast` / `GMEM_PATCH_FASTCLEAR_DEPTH` in `fd2_emit_tile_init`)
to localize clear-vs-render. No webOS reference exists for the GMEM depth-clear
sequence (the only captured webOS GLES clients were the 2D compositor and the
PalmPDK `simple` app, captured at the VSC level, not the per-tile depth clear).

  stdout, GL info on stderr. Env: `FD_CUBE=1` (depth cube), `FD_GRID=N` (NxN depth

- `/dev/shm/raw2png.py` (host) converts the raw dumps to PNG.
- Test on a **clean boot**; `gl-capture-md` lives in `/dev/shm` → re-upload after reboot.
