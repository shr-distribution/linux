Additional legacy CLK_VOTER pool (devices-msm8x60.c:1890-1909):
- `dfab_sdc_clk` (one voter per msm_sdcc.{1..5}) — feeds `dfab_clk`
- `dfab_usb_hs_clk` — feeds `dfab_clk`
- `dfab_dsps_clk` — feeds `dfab_clk`

- Mainline ebi1 / ebi1_a appear ONLY on AFAB. Legacy treats ebi1 as a *slave clock* of AFAB, plus exposes it via two voter aliases. Functionally equivalent.

## Section 5 — bwsum + arb mainline pipeline trace

Reading `msm8660_rpm_commit()` (msm8660.c:1159-1210):

1. Walks `provider->nodes`. For each node `n`:
   - `bw_bytes = max(avg_bw, peak_bw) × 1000` (icc_units_to_bps)
   - `bw_128k = bw_bytes >> 17` (clamped to ARB_BWMASK 0x7FFF)
2. If `qn->mas_port >= 0` and `def_ts > 0`:
   - `idx = (def_ts - 1) * nm + qn->mas_port`
   - `tier = bw_128k ? qn->mas_tier : ARB_TIER2`
   - `arb[idx] = (tier==TIER1 ? TIERMASK : 0) | bw_128k`
3. If `qn->slv_port >= 0`: `bwsum[qn->slv_port] = bw_128k`
4. Pack pairs of u16 into u32 via `msm8660_pack_rpm_data` (lines 1109-1151), then qcom_rpm_write to QCOM_RPM_*_FABRIC_ARB.

**Divergence vs legacy** (msm_bus_fabric.c:213-297, 407-457):

A. **Arb-row addressing.** Legacy sets `index = (hop->node_info->tier - 1) * nmasters + masterp` where `hop` is the SLAVE (line 430). So a TIER1 slave (EBI/SMI) puts the master's arb entry into row 1; a TIER2 slave (L2/SYSTEM_IMEM/MM_IMEM) puts it into row 2. Each master can therefore appear in **multiple** arb rows depending on which slave it is hitting.
   Mainline addresses arb[(def_ts-1)*nm + mas_port] for ALL traffic of a given master. **The master's arb is recomputed every commit and overwrites whatever row the master previously sat in, regardless of which slave the bandwidth is actually flowing to.**

B. **No-tier vs default-tier.** Legacy `msm_bus_fabric_update_bw` sets `tier = master_tier` for the first BW vote, then sticks at TIER1 once seen (line 433-439, sticky). Mainline always picks `qn->mas_tier` (line 1191) and the sticky-TIER1 behaviour is absent.

C. **Bwsum aggregation.** Legacy `bwsum[slavep] = link_info.sel_bw` (line 452-453) which is the *aggregated* per-slave bandwidth recomputed from the path tree. Mainline `bwsum[slv_port] = bw_128k` of THIS node only (line 1199). For a slave node, the framework sums avg_bw across all paths landing on it (via msm8660_icc_aggregate, line 1219-1228), so functionally similar.

D. **`>>17` flooring.** Mainline does pure right-shift `bw_bytes >> 17` (line 1183). Legacy uses `MSM_BUS_BW_VAL_FROM_BYTES` (msm_bus_board.h:119-121) which **rounds up** when the low 17 bits are non-zero. For our 512000 kBps vote = 512,000,000 bytes/sec, that's 0x1E84_8000, `>>17` = 0xF42 (3906) — exact. For 128000 kBps = 128,000,000 → 0x7A1_2000, `>>17` = 0x3D0 (976) — exact. **No rounding error on these specific values.**

E. **bw_128k=0 ⇒ TIER2 fallback.** Both mainline (line 1191) and legacy (line 442-443) reset tier to TIER2 on zero bandwidth. Matches.

F. **bwsum for slaves on path.** A node that is a slave receives `bw_128k` reflecting only its **own** aggregated avg_bw from icc_aggregate; gateways (`slv_port=-1`) drop out of bwsum entirely. Same as legacy.

G. **bwsum for non-final slaves on the chain.** For `<DFAB_MAS_SDC1, AFAB_SLV_EBI_CH0>`, the path is DFAB_MAS_SDC1 → dfab_to_sfab → sfab_to_dfab → sfab_to_appss → afab_to_system → slv_ebi_ch0. Mainline `slv_ebi_ch0.slv_port=0` on AFAB so AFAB's bwsum[0] sees the vote. Mainline `sfab_to_appss.slv_port=0` (msm8660.c:561) so SFAB's bwsum[0] (APPSS gateway slave) also gets the vote. Legacy: same — slave path nodes get bw too. Matches.

**Concrete observation for the eMMC WRITE failure:**

When sdcc1 calls icc_set_bw(512000, 512000) on the path `DFAB_MAS_SDC1 → … → slv_ebi_ch0`, mainline records:
- AFAB: `mas_port` only set for actual master nodes (mas_ampss_m0/m1, afab_to_mmss, afab_to_system gateway). None of these are SDC1, so **no AFAB arb entry is programmed for SDC1 traffic.** Only `bwsum[0] = 3906` and the implicit AFAB clk_set_rate rate-track.
- SFAB: same — SDC1 is not an SFAB master either. `sfab_to_appss.slv_port=0` so `bwsum[0]=3906`. **No SFAB arb entry for SDC1.**
- DFAB: `dfab_mas_sdc1.mas_port=-1` (msm8660.c:931). **No DFAB arb entry. No DFAB bwsum entry.** DFAB has rpm_resource=-1 so nothing is sent to RPM anyway. DFAB's bus clk just gets driven by the floor calc.

So for SDC1 traffic, the only thing RPM sees is "AFAB bwsum[0] += 3906" and "SFAB bwsum[0] += 3906". **No master ARB priority is added for the SDC traffic** — because SDC1 is not a master on AFAB/SFAB. Legacy webOS achieved the same effect by never programming SDC arbs either (legacy `msm_bus_board_8660.c` has no SDC master nodes). Both rely entirely on **bwsum-driven AFAB/SFAB clk_set_rate** to keep the path open.

## Section 6 — Concurrent eMMC WRITE + WiFi DL failure analysis

Failure signature (cited in question brief):
- mmci-pl18x 12400000.mmc: DATATIMEOUT: blksz=512 blocks=1040 flags=0x100 (WRITE)
- DATALEN=532480 DATACNT=56320 → completed 11% of payload (476,160 of 532,480 bytes UN-drained)
- errbits=(none latched) ⇒ ADM/DPSM stalled; no protocol error
- Concurrent: ~100 MB tele2 DL on WiFi sdcc4

**Why READ direction works but WRITE direction fails:**
- READ direction (5a87edb465e6 commit, qcom_adm.c:1577-1594): ADM ICC PORT1 vote was added; reads got the second SFAB master port arb slot. Reading drains EBI → ADM → SDCC FIFO at SDCC's pace; ADM provides credit-based backpressure.
- WRITE direction: data flows SDCC FIFO → ADM → SFAB → AFAB → EBI. The SDCC has a finite TX FIFO (typically 64×4 bytes). When the ADM cannot drain TX-side into EBI fast enough, the SDCC clock keeps shifting data out to the eMMC card, the TX FIFO underruns, DPSM data-window closes, and after DATA_TIMER expires we latch DATATIMEOUT.

**Where the audit findings intersect with WRITE-side ADM EBI bandwidth:**

1. **Section 4 / 5 result: SDC1 contributes ZERO ARB bandwidth on SFAB / AFAB.** Only `bwsum` accumulates. The actual SFAB/AFAB arbitration of CPU-side reads, MDP, GPU, ADM (PORT0+PORT1) is what gates the ADM's EBI bandwidth. **Critically, the ADM has TIER2 on both ports** (Section 1 SFAB row 4+5 and msm8660.c:444-462 ARB_TIER2). MDP is TIER1 on MMFAB; AFAB inbound gateway is TIER1 (mainline-specific elevation, mismatch noted in Section 1). So during concurrent activity, **MDP scanout and AMPSS gateway traffic both win TIER1 over the ADM's TIER2 — which is correct, BUT** the ADM never gets a TIER1 override even when servicing a critical SDCC drain.

2. **`afab_to_mmss.mas_tier = ARB_TIER1` (msm8660.c:351)** elevates the **APPSS→MMSS direction** to high priority. This is the MAINLINE-ONLY elevation not present in legacy (Section 1 flag). Under our failure, CPU-side accesses entering MMSS get TIER1 priority on AFAB — that pulls AFAB cycles AWAY from EBI fetches needed to drain the ADM's SDCC1 WRITE FIFO. **This is the most direct credible cause of the WRITE-side starvation that legacy does not exhibit.** Legacy left this gateway at TIER2; both CPU→MMSS and ADM→EBI competed at TIER2 and round-robined.

3. **`mmfab_to_appss.mas_tier = ARB_TIER1` (msm8660.c:859)** similarly elevates the AMPSS→SMI inbound traffic inside MMFAB to TIER1 (Section 1 flag). Again mainline-only. Combined with #2, mainline gives CPU-mapped SMI access a double-elevation across two fabrics that legacy doesn't.

4. **Section 5 finding: arb-row addressing.** Mainline writes ALL master arbs into row `(def_ts-1)`. For AFAB that's row 0 (EBI). For SFAB that's row 0 (APPSS gateway). Legacy by contrast distributes a master's arb across multiple rows based on which slave it currently hits. The practical effect for our failure: under heavy SFAB contention, mainline's TIER1 on `afab_to_mmss` is permanently registered in the EBI row, so EBI arbitration always sees it as TIER1 — even when there is no in-flight CPU→MMSS traffic. This biases EBI scheduling away from ADM PORT0/PORT1 (TIER2) **continuously**, not just when MMSS traffic actually exists.

5. **DFAB clk rate.** Section 3 confirmed mainline runs DFAB at ≥384 MHz floor (msm8660.c:71). Legacy ran DFAB at 64 MHz (msm_sdcc.c:1926). DFAB is not the bottleneck.

6. **EBI clk rate.** Mainline AFAB clks (bus + ebi1) all driven by `max(node_rate)` across the provider with 384 MHz floor (msm8660.c:1249-1273). Live ebi1 confirmed at 384 MHz. Legacy ran ebi1 at runtime-determined rates. **EBI clock is not the bottleneck** either.

**Most plausible single-line cause of the WRITE starvation:** the mainline-only `mas_tier = ARB_TIER1` on `afab_to_mmss` (msm8660.c:351), and the same on `mmfab_to_appss` (msm8660.c:859). Both gateways were elevated above the legacy baseline as a defensive fix for MDP under-runs ("Without this, MDP TIER1 priority earned in MMFAB is dropped at the AFAB boundary"). That fix solves an MDP problem at the cost of pushing ADM-PORT0/PORT1 TIER2 traffic into the back of the queue **on every AFAB cycle**, every time MMSS is alive (i.e., always — the display is always scanning out). The legacy baseline had AFAB cycling fairly between MMSS-gateway and ADM-via-SFAB-gateway, neither at TIER1.

## Section 7 — Ranked recommendations

### Fix 1 (HIGH confidence)
**File:line:** drivers/interconnect/qcom/msm8660.c:351
**Change:** Revert `afab_to_mmss.mas_tier = ARB_TIER1` → `ARB_TIER2`.
**Expected behaviour:** AFAB arbiter treats the MMSS inbound gateway at default tier. ADM PORT0/PORT1 sees fair EBI access during MDP+SDC+WiFi load. The MDP-underflow regression the elevation was meant to prevent must be re-validated under concurrent eMMC WRITE + WiFi DL. If MDP underflow returns, the *correct* trade is to elevate the SPECIFIC slave-row (not the gateway master) — i.e., gain back legacy's per-slave-tier semantics (Section 5 finding A) so MDP wins in the MMSS arb row WITHOUT also winning in the EBI arb row.
**Confidence:** HIGH — direct cause-effect match against failure signature.
**Failure mode if wrong:** MDP PRIMARY_INTF_UDERRUN reappears under heavy I/O. Mitigation: clock MDP at higher MMFAB rate or revert.

### Fix 2 (MEDIUM confidence)
**File:line:** drivers/interconnect/qcom/msm8660.c:859
**Change:** Revert `mmfab_to_appss.mas_tier = ARB_TIER1` → `ARB_TIER2`.
**Expected behaviour:** MMFAB arbiter stops biasing the APPSS-inbound gateway at TIER1. CPU memremap_wc accesses into SMI drop back to default priority, freeing MMFAB cycles for MDP/VFE/codec — and indirectly relieving AFAB->EBI contention. Independent of Fix 1; both elevations stack.
**Confidence:** MEDIUM — second-order effect on the eMMC failure (MMFAB does not directly carry SDC traffic), but #1 alone may not fully close the gap if the AFAB contention is downstream of MMFAB scheduling.
**Failure mode if wrong:** mild CPU-side latency increase when reading from SMI mappings (display BO read-back / debugging only).
